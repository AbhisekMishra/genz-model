Build log · fine-tuning postmortem

Teaching a 1.5B model to say "no cap" and mean it

A working record of fine-tuning Qwen2.5-1.5B-Instruct into a genz-slang persona + translator model with QLoRA, on a single 8 GB laptop GPU, and the four rounds of debugging it took to make the slang accurate, not just present. Written to study from before an interview, not to be read top to bottom in one sitting.

01 · the brief

What was being built

A small open-source LLM fine-tuned for two behaviors selected by system prompt: a genz-slang persona chatbot, and a style-transfer tool that rewrites plain text into genz slang while preserving meaning. Trained locally, no API budget, published to Hugging Face with a real model card. The interesting part wasn't the training run itself — it was discovering the model was confidently wrong about several slang terms, and the iterative work to fix that without breaking anything else.

02 · decisions & why

Three choices worth defending in an interview

DecisionReasoning
Qwen2.5-1.5B-Instruct over larger/other models Apache 2.0 (redistributable — the 3B sibling in the same family isn't), ungated (no manual access request, unlike Llama), and small enough to fit 4-bit-quantized in 8GB VRAM with headroom to spare.
QLoRA over full fine-tuning Full fine-tuning needs gradients + optimizer state + activations for every parameter — easily 20–30GB+ for a model this size. QLoRA freezes the base model, quantizes it to 4-bit, and trains small injected adapter matrices instead — fits comfortably on one consumer GPU.
Synthetic + grounding data over scraping No LLM API budget ruled out runtime generation at scale. Hand-authored a pilot batch for tone approval, then parallelized authoring across independent writers with a fixed schema, grounded in real HF slang datasets for vocabulary authenticity rather than inventing terms.
03 · the technique

LoRA / QLoRA, in one breath

LoRA (Low-Rank Adaptation): freeze the base model's weights entirely, and inject small trainable low-rank matrices into specific layers — here, every attention and MLP projection. Only those injected matrices get gradients. The result here trained 18.4M of 1.56B parameters (1.2%), which is why it fits on a laptop GPU and trains in minutes, not hours.

The "Q": the frozen base weights are loaded in 4-bit (NF4 format, double-quantized) so they take roughly a quarter of the memory of full precision, while the small LoRA adapters still train in bf16 for numerical stability. Quantizing the part that doesn't change and keeping full precision on the part that does is the whole trick.

04 · data pipeline

~4,300 examples, five categories

Chat-format JSONL (system / user / assistant) across five categories: casual persona chat, slang-translation pairs, roleplay reactions, slang Q&A, and edge cases — formal, factual, and crisis-adjacent prompts specifically included so the model learns not to slang-ify everything. Real Hugging Face slang datasets (e.g. MLBtrio/genz-slang-dataset) were pulled in as vocabulary grounding, not dumped straight into training.

Scaling technique: rather than authoring serially, generation was parallelized across independent writers, each owning one category slice and a fixed JSON schema, merged afterward with exact-duplicate removal and a 90/10 stratified train/val split (stratified by category so validation isn't skewed toward whichever category is largest).

05 · the debugging story

Why "it works" isn't the same as "it's right"

The training run itself was uneventful — loss dropped cleanly, no divergence. The real engineering happened in evaluation: a held-out prompt set (persona, translation, slang Q&A, and plain factual questions to catch catastrophic forgetting) surfaced that the model was confidently wrong about specific slang definitions — "rizz" came back as something like "loud and boisterous" instead of charisma.

Root cause

The training data had the correct definition — but that exact term appeared only once or twice across ~4,000 examples. LoRA only updates 1.2% of the model's parameters; that's nowhere near enough repeated signal to overwrite a base model's existing (and apparently wrong) prior belief about a token sequence. Fine-tuning nudges a distribution — it doesn't overwrite a fact unless that fact shows up repeatedly, in varied phrasing.

Four reinforcement rounds

1
Fix the obvious break fixed

~70 examples targeting "rizz" / "no cap" / "mid" with varied phrasing, not one canonical sentence repeated. Retrained, re-tested, confirmed correct.

2
Broad stress test, 65 new prompts 13+ new misses found

Tested ~50 terms never touched in training, plus in-context usage (does the model correctly restrict "ick" to romantic turn-offs, not general embarrassment?). Surfaced sigma, beige flag, yeet, simp, periodt, boy math, canon event, and more — plus misapplied terms.

3
The sampling-noise detour methodology fix

A follow-up test made it look like previously-fixed terms had regressed. Re-ran with greedy decoding instead of temperature sampling — most "regressions" disappeared. The earlier test wasn't measuring the model's knowledge, it was partly measuring sampling randomness.

4
The stubborn four fixed with heavier data

Sigma, canon event, "booked and busy," and "sending me" resisted light reinforcement (~5 examples) because they collide with far more common existing meanings (sigma = math symbol, canon = fiction term). ~15 examples each, with explicit contrastive corrections ("this is not about a TV show"), finally moved them — and held up on phrasings never seen in training.

The methodology point to lead with

Sampling (temperature/top-p) vs. greedy decoding is not a minor detail — it changes what an eval is actually measuring. Sampling draws randomly from the output distribution; for a definitional question you usually want the model's single most-confident answer, which is what greedy decoding gives you. Confusing the two turned a real signal into apparent noise for an entire debugging round.

06 · shipping it

Deployment

Merged the trained LoRA adapter into the base weights (merge_and_unload()) to produce a standalone model requiring no extra library to load, and published both that merged repo and a lightweight adapter-only repo — the adapter is a few tens of MB and lets anyone apply it to the base model themselves; the merged repo is a few GB but works with a single from_pretrained() call. Verified the published model by downloading it fresh from the Hub (not local cache) and confirming outputs matched what was tested pre-upload.

07 · glossary

Terms to have cold

LoRA
Low-Rank Adaptation. Freeze the base model; train small injected low-rank matrices instead of the full weight matrices. Drastically cuts trainable parameters and memory.
QLoRA
LoRA plus 4-bit quantization of the frozen base model. The adapters still train in higher precision (bf16 here); only the frozen backbone is compressed.
4-bit NF4 quantization
A quantization format tuned for normally-distributed neural network weights. "Double quantization" additionally quantizes the quantization constants themselves for further memory savings.
Gradient accumulation
Simulating a larger batch size than fits in memory by accumulating gradients over several small forward/backward passes before an optimizer step. Here: batch 4 × accumulation 8 = effective batch 32.
Gradient checkpointing
Trades compute for memory — instead of storing every layer's activations for the backward pass, recompute them on demand. Slower per step, much lower peak memory.
Catastrophic forgetting
Fine-tuning on a narrow task degrading a model's general capability. Guarded against here with plain factual prompts in the eval set that have nothing to do with slang.
Overfitting signal
Train loss continuing to fall while eval loss plateaus or rises — the model is memorizing training examples rather than generalizing further.
Chat template
The exact token structure (role markers, special tokens) a model was instruction-tuned to expect. Training and inference data must match it, applied via tokenizer.apply_chat_template().
Sampling vs. greedy decoding
Sampling (temperature / top-p) draws randomly from the model's output probability distribution — good for varied, creative generation, noisy for evaluating factual correctness. Greedy decoding always takes the single highest-probability token — the model's most confident, deterministic answer.
Adapter vs. merged model
An adapter-only release ships just the small trained LoRA matrices (needs the base model + peft to use). A merged release bakes the adapter into the base weights into one standalone model — bigger file, zero extra dependency.
08 · rehearsal

Likely interview questions

Why QLoRA instead of full fine-tuning?
Memory. Full fine-tuning needs gradients and optimizer state for every parameter — tens of GB for even a 1.5B model. QLoRA freezes and quantizes the base model to 4-bit and only trains ~1% of parameters as small adapters, which fits an 8GB consumer GPU.
How did you evaluate a fine-tune with no ground-truth benchmark?
Built a fixed held-out prompt set spanning the model's intended behaviors plus generic factual prompts as a forgetting check, and did structured qualitative comparison — base vs. fine-tuned, same prompts. For anything definitional (slang meanings), correctness could be checked directly against known real-world definitions.
Tell me about a bug you found during this project.
The model gave a confidently wrong definition for "rizz" despite the correct definition being in the training data. Root cause: it only appeared once or twice in ~4,000 examples — not enough repetition for a low-rank adapter update to override the base model's existing prior. Fixed by reinforcing with more examples in varied phrasings, not just repeating the same sentence.
How do you know a fix actually generalized, rather than just memorizing the training sentence?
Tested with phrasings never seen during training — e.g. trained on "someone said i ate that outfit," tested with "did you eat that fit" — and confirmed the model applied the concept correctly to the new phrasing, not just the exact training sentence.
What would you do differently with more budget or time?
Use a larger base model or full LLM API for higher-quality synthetic data generation at scale instead of hand-authoring; add an automated regression suite (fixed prompt set + greedy decoding + string/semantic matching) instead of manual read-throughs each round; consider RLHF/DPO-style preference data for the two-mode behavior instead of only supervised fine-tuning.
